# AI-Stylist: план локального прототипа

Документ для передачи модели-разработчику. Сначала прочитать целиком, затем выполнять этапы по порядку. Это план, а не отчёт о готовой реализации. На момент составления в проекте нет кода, модели локально не запускались.

## 1. Цель и согласованный объём

Нужен простой работающий прототип на Python к сроку «через день». Приоритет — пройти полный пользовательский сценарий; высокая точность и оформление вторичны.

Согласовано пользователем:

- Локальное веб-приложение, интерфейс на Streamlit.
- Пока только женские рекомендации.
- Загрузка фотографии и анализ формы лица.
- MediaPipe для обнаружения лица и ключевых точек.
- Отдельная готовая нейросеть для классификации формы лица; ViT допустим.
- Тип фигуры по введённым меркам, с помощью правил.
- Рекомендации по одежде и причёскам с учётом предпочтений.
- Общая стиль-карта, объяснения, ручное исправление категорий.
- Использование готовых моделей без собственного обучения на этом этапе. Обучаемой рекомендательной системы нет.
- Источники рекомендаций нужно найти и использовать, а не сочинять стилистические правила.

Не реализовывать: анализ цвета и цветотип, сегментацию кожи/глаз/волос, макияж, пирсинг, анализ фото тела, гардероб, виртуальную примерку, обучение, сбор обратной связи для обучения.

Не добавлять аккаунты, БД, историю пользователей, чат, LLM, внешние API для обработки фотографий, отдельный frontend/backend, Docker и публикацию. Эти компоненты не нужны для согласованного локального сценария.

Иллюстрации не согласованы. Рабочее упрощение первой версии — текстовые рекомендации со ссылками. Не тратить срок на поиск картинок и генерацию изображений.

## 2. Что пользователь должен получить

1. Открывает локальный адрес Streamlit.
2. Загружает JPG или PNG с одним лицом анфас.
3. Нажимает «Анализировать фото».
4. Получает предполагаемую форму лица и оценки классов нейросети.
5. При желании вручную меняет форму лица; исходное предсказание сохраняется отдельно.
6. Вводит обхваты груди, талии и бёдер в сантиметрах.
7. Выбирает стиль одежды: деловой, повседневный, спортивный или неформальный — эти варианты взяты из исходного описания проекта.
8. Выбирает пожелание по длине причёски: без ограничения, короткая, средняя, длинная. Это минимальное техническое представление пожеланий, а не дополнительная аналитическая функция.
9. Получает предполагаемый тип фигуры и может исправить его.
10. Нажимает «Сформировать стиль-карту».
11. Видит форму лица, тип фигуры, свои предпочтения и подходящие рекомендации по одежде и причёскам. У каждой рекомендации есть объяснение и источник.

Рекомендации по причёске зависят от формы лица и пожелания длины. Рекомендации по одежде — от типа фигуры и стиля. Не создавать несуществующие связи, например определять фасон брюк по форме лица.

## 3. Архитектура

```text
JPG/PNG → Pillow → MediaPipe → область лица → ViT → форма лица
                                                    ↓
                                           ручная корректировка
                                                    ↓
                                база рекомендаций по причёскам

Мерки → проверка → правила типа фигуры → ручная корректировка
                                                    ↓
Стиль одежды ───────────────────────→ база рекомендаций по одежде

Результаты + предпочтения + источники → стиль-карта в Streamlit
```

Два компонента с нейросетями: MediaPipe и отдельный классификатор формы лица. MediaPipe не определяет сезонный цветотип, тип фигуры или класс формы лица. Рекомендательный модуль работает по данным и правилам.

## 4. Стек и зависимости

Начальный кандидат — Python 3.11, если он доступен и для платформы устанавливаются необходимые пакеты. Версию не считать проверенной до установки.

Runtime-зависимости:

- `streamlit` — UI;
- `mediapipe` — Face Landmarker;
- `torch`, `transformers` — ViT;
- `Pillow`, `numpy` — изображения и массивы;
- `huggingface_hub` — разовая загрузка готового классификатора.

Dev-зависимость: `pytest` для нескольких содержательных проверок правил и выбора рекомендаций. JSON, dataclasses, logging, hashlib брать из стандартной библиотеки.

Не добавлять TensorFlow, OpenCV, torchvision, scipy, scikit-learn и accelerate, если реальный запуск выбранного решения их не требует. Не устанавливать их «на всякий случай».

Начать с CPU. Не использовать `device_map="auto"`, CUDA, MPS, fp16 и квантование в первой версии. Модели небольшого прототипа сначала должны корректно работать в обычном CPU-режиме; время измерить на реальном ноутбуке.

После успешного запуска зафиксировать реально проверенные версии зависимостей. Не придумывать номера версий и не переносить весь глобальный `pip freeze` в requirements.

## 6. Общие контракты данных

Использовать стабильные английские ID внутри программы и русские подписи в UI. Не сравнивать отображаемые русские строки в алгоритмах.

### Форма лица

Ожидаемые смысловые категории кандидата:

| ID приложения | Подпись |
|---|---|
| `heart` | Сердцевидная |
| `oblong` | Продолговатая |
| `oval` | Овальная |
| `round` | Круглая |
| `square` | Квадратная |

Порядок классов читать из `model.config.id2label`. Никогда не считать, что порядок в этой таблице совпадает с индексами выходов сети. Не смешивать `oblong` и `oval`.

### Тип фигуры

ID: `hourglass`, `pear`, `inverted_triangle`, `rectangle`, `apple`. Русские подписи: «Песочные часы», «Груша», «Перевёрнутый треугольник», «Прямоугольник», «Яблоко». Если правила не дают однозначного результата, `predicted_shape=None`, UI предлагает выбрать вручную. Не вводить фиктивный класс модели «неизвестно».

### Результаты

В `schemas.py` определить примерно следующие структуры. Названия можно сохранить буквально:

```python
BodyMeasurements(bust_cm: float, waist_cm: float, hips_cm: float)

FaceAnalysis(
    predicted_shape: str,
    scores: dict[str, float],    # Все 5 классов, значения 0..1
    model_id: str,
    model_revision: str,
)

BodyAnalysis(
    predicted_shape: str | None,
    matched_rule_ids: list[str],
    explanation: str,
)

Recommendation(
    id: str,
    title: str,
    description: str,
    reason: str,
    source_ids: list[str],
)
```

Фактическое предсказание и ручной выбор хранить отдельно. Эффективное значение для рекомендаций: ручной выбор, если он есть, иначе предсказание. В UI явно различать эти два источника.

Ожидаемые ошибки пользовательского ввода представить отдельными исключениями, например `InvalidImageError`, `NoFaceError`, `MultipleFacesError`, `InvalidMeasurementsError`, `ModelUnavailableError`. Не возвращать случайный класс при исключении.

## 7. Этап 1 — проверить модели до разработки интерфейса

### 7.1. Проверить окружение

1. Прочитать применимые `AGENTS.md`, если они появятся.
2. Проверить ОС, архитектуру процессора, версию Python и наличие свободного места. Не выводить секреты и содержимое чужих директорий.
3. Создать `.venv` внутри проекта.
4. Установить минимальные зависимости и проверить импорты.
5. Проверить, что доступны готовые пакеты MediaPipe и PyTorch для этой платформы. Не начинать длительную сборку MediaPipe из исходников ради прототипа.

### 7.2. Получить веса

Основной кандидат классификатора: `metadome/face_shape_classification`.

Источники:

- Карточка и файлы: https://huggingface.co/metadome/face_shape_classification
- MediaPipe: https://developers.google.com/edge/mediapipe/solutions/vision/face_landmarker?tab=Python
- Совместимость: https://developers.google.com/edge/mediapipe/solutions/setup_python

Действия:

1. Проверить карточку, список файлов, config и processor классификатора, доступность весов и условия использования. Если лицензия не указана, записать «не указана», а не приписывать открытую лицензию. Не распространять чужие веса как свои.
2. Скачать Face Landmarker по ссылке из официальной документации, сохранить `.task`.
3. Скачать снимок классификатора в `models/face_shape/`, включая веса, config и конфигурацию image processor.
4. Записать фактическую ревизию классификатора и URL/версию MediaPipe-артефакта в `MODEL_NOTES.md`.
5. Повторный запуск скрипта не должен заново скачивать исправные веса. Существование одного пустого файла не считать успешной загрузкой.
6. В runtime загружать классификатор из локальной директории с `local_files_only=True`. Интернет нужен при подготовке, фотографии никуда не отправляются.
7. Не включать `trust_remote_code=True`. Предпочитать safetensors, если такие веса доступны.

### 7.3. Выполнить реальный инференс

1. Использовать `AutoImageProcessor` и `AutoModelForImageClassification` для выбранной модели.
2. Вызвать `model.eval()`, инференс выполнять под `torch.inference_mode()`.
3. Получать входной тензор через родной image processor. Не задавать от себя средние RGB, std и размер входа.
4. Применить softmax к logits ровно один раз. Сопоставить индексы и подписи через config.
5. Если модель выдаёт `LABEL_0` и подобные названия, найти документированное соответствие классов. Не угадывать его по одной фотографии или алфавиту.
6. Запустить полный проход на разрешённой к использованию фотографии с одним лицом. Убедиться, что результат содержит пять конечных оценок с суммой около 1.
7. Измерить время первого и повторного проходов; записать реальные значения. Не обещать скорость до измерения.
8. Проверить повторную загрузку весов без сети.

Готовность этапа: есть настоящий результат MediaPipe и настоящий результат ViT на одном изображении. Успешного импорта недостаточно.

Если нет доступного разрешённого фото, довести код и проверку моделей без него, затем запросить фото для реального прогона; не выдавать синтетический или замоканный результат за успешную проверку на человеке.

Если кандидат не запускается или не имеет определяемых меток, сначала проверить официальные инструкции и исправить загрузку. Если это не помогает, подобрать другую готовую модель той же задачи и документировать замену. Не обучать свою сеть, не заменять ViT правилами и не подменять инференс заглушкой.

## 8. Этап 2 — обработка фото и анализ лица

### `images.py`

Предлагаемые функции:

```python
load_image(file_bytes: bytes) -> PIL.Image.Image
crop_face(image: PIL.Image.Image, landmarks) -> PIL.Image.Image
```

Порядок `load_image`:

1. Проверить, что файл непустой. Технический лимит первой версии — 10 МБ; это ограничение приложения, а не требование модели.
2. Декодировать через Pillow; расширение файла не считать доказательством формата. Принимать JPEG и PNG.
3. Ограничить число пикселей, например 20 млн, и не отключать защиту Pillow от огромных изображений.
4. Применить `ImageOps.exif_transpose` до любых измерений.
5. Для прозрачности использовать белую подложку, затем привести к RGB.
6. Уменьшить слишком большое изображение с сохранением пропорций, например до 1600 пикселей по длинной стороне. Исходные и уменьшенные координаты не смешивать.
7. Не сохранять загруженный файл на диск.

### MediaPipe

1. Использовать Tasks API `FaceLandmarker`, режим `IMAGE`, CPU.
2. Установить `num_faces=2`, чтобы можно было отклонить фото с несколькими обнаруженными лицами. При значении 1 проверить это невозможно.
3. Blendshapes и матрицы трансформаций не запрашивать: они не нужны.
4. Pillow RGB преобразовать в непрерывный NumPy-массив `uint8`, затем в `mp.Image` с форматом SRGB.
5. При 0 обнаруженных лицах показать просьбу загрузить другое фото; при 2 — просьбу оставить на снимке одного человека. Это проверка обнаруженных лиц, а не гарантия обнаружения всех людей на снимке.
6. Не реализовывать оценку возраста, пола, этничности, эмоций и привлекательности. Аудитория выбрана пользователем, её не требуется определять по фотографии.

### Подготовка области лица для ViT

1. Сначала проверить, описана ли предобработка в карточке/коде модели. Если да — воспроизвести её.
2. Если точный crop не описан: взять bounding box по координатам ключевых точек лица, расширить на 20% с каждой стороны и обрезать по границам фото. Это инженерная эвристика прототипа, не подтверждённая предобработка автора модели; отметить её в `MODEL_NOTES.md`.
3. Координаты нормализованных точек преобразовывать с использованием ширины/высоты именно текущего изображения. Ограничить координаты допустимыми пределами.
4. Проверить, что crop имеет положительные размеры.
5. Передать crop родному processor. Не растягивать вручную до произвольного размера и не добавлять выравнивание головы, если оно не требуется документированной обработкой.
6. Показать crop в раскрывающемся блоке «Область анализа» — это помогает увидеть ошибочную обрезку.

Геометрические коэффициенты формы лица в этой версии не нужны: категорию определяет отдельная сеть. Не делать параллельный классификатор по расстояниям.

Оценки softmax подписывать как «оценки модели», не как доказанную точность или вероятность правильности. Можно показать все пять значений. Не придумывать откалиброванный порог уверенности.

Наклон и плохое освещение описать в короткой подсказке перед загрузкой. Автоматическую сложную проверку качества фото отложить.

## 9. Этап 3 — тип фигуры по меркам

Функция:

```python
classify_body(measurements: BodyMeasurements) -> BodyAnalysis
```

Источник численных критериев: https://theconceptwardrobe.com/build-a-wardrobe/determine-your-body-shapes

Использовать только обхваты груди, талии и бёдер. Рост, вес и плечи для выбранной первой реализации не требуются. В интерфейсе дать инструкцию: грудь и бёдра по наиболее выступающей части, талия по наиболее узкой; единицы — сантиметры.

Обозначения: `B` — грудь, `W` — талия, `H` — бёдра.

Валидация: все три значения заданы, числовые, конечные и строго больше нуля. Не требовать `W < B` или `W < H`: это не универсально и помешает категории «яблоко». Не вводить медицинские диапазоны и выводы.

Из источника:

- Песочные часы: грудь и бёдра отличаются в пределах 5%; талия минимум на 25% меньше груди и бёдер.
- Прямоугольник: грудь и бёдра отличаются в пределах 5%; талия менее чем на 25% меньше груди.
- Груша: бёдра минимум на 5% больше груди; талия — наименьшая мерка.
- Перевёрнутый треугольник: грудь более чем на 5% больше бёдер; бёдра — наименьшая мерка.
- Яблоко: талия не меньше груди, грудь больше бёдер; бёдра до 5% меньше груди.

Стилистический текст не задаёт все детали границ и может давать пересечения. Ниже — явная консервативная операционализация для кода, а не утверждение о научном стандарте:

```python
balanced = max(B, H) / min(B, H) <= 1.05

hourglass = balanced and W <= 0.75 * B and W <= 0.75 * H
rectangle = balanced and 0.75 * B < W < min(B, H)
pear = H >= 1.05 * B and W < min(B, H)
inverted_triangle = B > 1.05 * H and H < W and H < B
apple = 0.95 * B <= H < B and W >= B
```

`rectangle` содержит дополнительное ограничение `W < min(B,H)`, чтобы не присваивать его явно центральному силуэту. Симметричная формула `balanced` также является техническим уточнением выражения «в пределах 5%». Записать эти решения в `SOURCES.md` рядом с исходными формулировками.

Не менять сравнение для `inverted_triangle` с `H < W` на `W < H` незаметно: источник называет бёдра наименьшей меркой. Это ограничивает применимость данной схемы по трём обхватам. Если понадобится более широкая классификация, сначала подобрать другой документированный алгоритм, а не корректировать правила по интуиции.

Вычислять все совпадения:

- Ровно одно — вернуть категорию и понятное объяснение по меркам.
- Нет совпадений — вернуть `None`, объяснить, что правила не дают однозначной категории, предложить ручной выбор.
- Несколько совпадений, в том числе на границах 5%, — также вернуть `None` и перечислить совпавшие категории. Не разрешать коллизию случайным порядком `if`.

Это намеренно осторожный алгоритм: он не обязан принудительно классифицировать каждое тело. Не добавлять «точность 90%», медицинские заключения и оценку привлекательности.

## 10. Этап 4 — база рекомендаций с источниками

### Источники

Начальные проверенные страницы:

1. The Concept Wardrobe — описание типов и численные критерии:
   https://theconceptwardrobe.com/build-a-wardrobe/determine-your-body-shapes
2. Stitch Fix — одежда для типов фигуры:
   https://www.stitchfix.com/women/blog/style-guide/find-fit-for-your-body-type/
3. L’Oréal Paris — причёски для овального, круглого, сердцевидного и квадратного лица:
   https://www.lorealparisusa.com/beauty-magazine/hair-style/medium-hairstyles/haircuts-face-shape

Пробел: основная статья L’Oréal не покрывает продолговатую форму лица. До заполнения этой категории найти отдельный источник с явными рекомендациями для oblong/long face. Не считать oval и oblong одинаковыми только потому, что другая статья смешивает термины.

В Stitch Fix для непокрытых рекомендаций перейти в связанные подробные руководства соответствующего типа фигуры. Для стилей одежды найти статьи, явно описывающие соответствующий стиль. Не приписывать найденным страницам советы, которых в них нет.

Для каждой записи `SOURCES.md` хранить ID, название страницы, URL, дату проверки, какие утверждения и категории из неё взяты. Отличать перевод/пересказ источника от технической разметки разработчика.

Не копировать статьи и изображения целиком. Кратко пересказывать только необходимые советы, добавляя ссылку. Не извлекать из статей рекламу косметических средств.

### Формат `hairstyles.json`

Массив записей:

```json
{
  "id": "unique_stable_id",
  "title": "Краткое название",
  "face_shapes": ["round"],
  "length": "medium",
  "description": "Что за стрижка или укладка",
  "reason": "Краткое объяснение из источника",
  "source_ids": ["source_id"]
}
```

Допустимые длины: `short`, `medium`, `long`. «Без ограничения» — значение фильтра, а не длина записи.

Минимальное покрытие: у каждой из пяти форм есть варианты каждой длины, если источник их подтверждает. Записи могут относиться к нескольким формам, если это явно обосновано. Не раздувать число записей ради количества.

### Формат `clothing.json`

```json
{
  "id": "unique_stable_id",
  "title": "Название вещи или сочетания",
  "body_shapes": ["hourglass"],
  "styles": ["business", "casual"],
  "description": "Конкретный фасон или сочетание",
  "reason": "Почему этот фасон предложен для этих пропорций",
  "source_ids": ["body_guide", "style_guide"]
}
```

Стиль ID: `business`, `casual`, `sporty`, `informal`.

Цель покрытия: хотя бы один обоснованный вариант для каждого типа фигуры и каждого из четырёх стилей. Одну запись можно использовать в нескольких сочетаниях. Для спорного отнесения к стилю найти источник или оставить явный пробел; не размечать всё всеми стилями ради прохождения проверки.

База должна содержать готовые объяснения. Не нужен генератор текста или LLM. У одного совета для нескольких категорий объяснение должно действительно подходить всем указанным категориям; иначе разделить запись.

### Логика выбора

```python
get_hairstyles(face_shape, length_preference) -> list[Recommendation]
get_clothing(body_shape, style) -> list[Recommendation]
```

Простая фильтрация, стабильный порядок по JSON, без случайности и обучаемого ранжирования. В UI показать до трёх результатов каждого раздела; если подходит один — показать один, не дописывать ещё два.

Если после фильтра пусто, явно сообщить «В базе пока нет рекомендаций для такого сочетания». Не игнорировать выбранный стиль или длину молча. Для причёсок можно предложить пользователю самому выбрать «Без ограничения».

Если стиль неформальный требует уточнений, использовать консервативный вариант из найденного источника и описать границы в README. Не добавлять автоматически десятки субкультур и дополнительные анкеты.

## 11. Этап 5 — Streamlit

Одна страница, русский интерфейс, стандартные компоненты. Не разрабатывать дизайн-систему.

### Разделы страницы

1. Название и короткое описание.
2. Подсказка к фото: один человек, анфас, равномерное освещение, лицо видно.
3. Загрузка JPG/PNG, превью, кнопка анализа.
4. Результат анализа, оценки модели, ручной выбор формы лица с опцией «Использовать результат модели».
5. Форма с тремя мерками, стилем одежды и предпочтением длины волос.
6. Результат правил типа фигуры и ручная корректировка с опцией «Использовать результат расчёта».
7. Кнопка формирования стиль-карты.
8. Стиль-карта: категории, источник категории (авто/вручную), предпочтения, два раздела рекомендаций, ссылки.

Уточнение потока: пересчёт мерок должен сначала обновить `BodyAnalysis`, затем применить ручной выбор и сформировать карту. Не требовать отдельного перехода на другую страницу.

### Состояние и загрузка моделей

- Модели загружать через `st.cache_resource`; пользовательские фото там не хранить.
- FaceLandmarker может иметь внутреннее состояние; если один экземпляр разделяется, обернуть вызов в lock или организовать экземпляр на сессию. Не считать его автоматически потокобезопасным.
- Изображение и результат анализа хранить только в `st.session_state` текущей сессии.
- Анализ изображения запускать по кнопке; изменение стиля не должно повторно запускать ViT.
- Считать SHA-256 байтов загруженного файла. При новом фото сбрасывать старое предсказание, ручную корректировку лица и готовую карту.
- При изменении мерок сбрасывать старую ручную корректировку типа фигуры. Изменение предпочтений должно пересобирать/скрывать старую карту, чтобы она не противоречила текущим полям.
- Не ставить `st.cache_data` на пользовательские фото ради удобства.
- Спиннер во время анализа. Ошибки показывать понятным текстом без traceback; технические сведения писать в локальный лог без фото и мерок.
- Если модель отсутствует, показать команду подготовки весов и остановить автоматический анализ, а не скачивать веса при каждом rerun.
- Ручной режим может позволять просмотреть рекомендации при недоступной модели, но должен явно обозначаться как ручной и не считаться выполнением нейросетевого сценария.

## 12. Этап 6 — проверка

### Несколько автоматических проверок

Не писать тесты ради каждой строчки. Проверить наиболее рискованные правила и согласованность базы.

`test_body.py`:

- Примеры, попадающие в каждую из пяти категорий по записанным формулам.
- Точные границы 5% и 25% и случаи сразу по обе стороны.
- Нет совпадения; пересечение правил — результат не выбирается произвольно.
- Нулевые, отрицательные, NaN и бесконечные значения отклоняются.
- Пропорциональное изменение всех трёх мерок не меняет результат классификации.

`test_recommendations.py`:

- Все ID уникальны, обязательные поля заполнены, категории допустимы, `source_ids` существуют.
- Фильтр не выдаёт запись другой формы, длины или стиля.
- Покрытие всех пяти форм лица и типов фигуры, с проверкой сочетаний предпочтений.
- Пустой результат обрабатывается явно.

Модели в pytest не скачивать. Реальный инференс проверить отдельно через `scripts/smoke_face.py`; замоканная сеть не подтверждает работоспособность модели.

### Ручная приёмка

1. На разрешённом фото одного человека полный путь даёт реальные оценки ViT и стиль-карту.
2. Фото без лица даёт понятное сообщение, не выдуманный результат.
3. Фото с двумя обнаруживаемыми лицами отклоняется.
4. Повреждённый файл и слишком большой файл не обрушивают страницу.
5. Фото с EXIF-поворотом показывается и анализируется в правильной ориентации.
6. Ручная смена формы лица и типа фигуры меняет соответствующие рекомендации.
7. Смена фото не оставляет результат предыдущего лица; смена мерок не оставляет старую категорию/карту.
8. Смена стиля и длины фильтрует рекомендации без повторного инференса.
9. Перезапуск приложения после загрузки моделей работает без доступа к сети.
10. Веса отсутствуют — показана инструкция, приложение не изображает успешный анализ.

Записать, какие проверки реально выполнены и какие не выполнены из-за отсутствия тестовых фото. Не писать «всё протестировано», если проверены только чистые функции.

## 13. Данные, датасеты и ограничения

Обучение не проводится: обучающий датасет, LFW, разделение train/val/test, Kaggle и метрики обучения в этот прототип не входят.

Для функциональной проверки достаточно небольшого набора разрешённых фото с разными ситуациями. Не скачивать случайные лица из поиска без проверки права использования. Не помещать личные фото в Git.

Функциональная проверка не измеряет точность классификации. Для заявлений о качестве нужен отдельный размеченный набор; сейчас не обещать проценты. Числа из карточки модели не представлять как измеренную точность нашего приложения.

В README указать: чувствительность к освещению/ракурсу, условность стилистических категорий, возможность ручного исправления, ограниченность базы, неизвестные детали обучения готовой модели и эвристику crop, если она применяется.

Фото и мерки обрабатываются локально в памяти. Не обещать криптографического удаления из RAM и не писать о бессрочном хранении. Подготовка весов требует интернета; обычный инференс — нет.

## 14. Порядок работы под срок «через день»

Это порядок приоритетов, а не гарантия длительности этапов.

### Первый рабочий блок / первый день

1. Окружение, веса и реальный инференс — в первую очередь.
2. Контракты, обработка фото, проверка одного лица, классификация.
3. Правила фигуры и проверка пограничных случаев.
4. Минимальная страница, на которой видны оба результата анализа.

Контрольная точка: фото действительно проходит через MediaPipe и ViT, мерки дают результат или честную неопределённость. Если этого нет, не переключаться на украшение UI.

### Второй рабочий блок / оставшееся время

1. Закрыть пробел источника для oblong и собрать базу рекомендаций.
2. Реализовать фильтрацию предпочтений и ручное исправление.
3. Собрать стиль-карту и обработку ошибок.
4. Пройти приёмку и подготовить README с проверенными командами.

При дефиците времени сокращать оформление и число рекомендаций на сочетание. Не вырезать одну из двух веток (лицо/причёски и фигура/одежда), не вырезать ViT, не добавлять обучение и не заполнять базу неподтверждёнными советами.

Если не удаётся запустить нейросетевой компонент, честно обозначить конкретную причину и выполненные шаги. Не выдавать частичный ручной прототип за выполнение согласованного объёма.

## 17. Как добавить отложенные функции позже

Сохранять модули независимыми; не писать расширения сейчас.

- Цветовой анализ может стать отдельным модулем и новым полем стиль-карты.
- Макияж и пирсинг потребуют отдельных данных рекомендаций и источников.
- Обучаемая рекомендательная система позже сможет заменить функции выбора, получая те же категории и предпочтения.
- Новые модели можно подключить через модуль `face.py`, сохранив внутренние ID категорий или явно расширив контракт.

Не создавать заранее инфраструктуру для этих возможностей. Достаточно не смешивать UI, инференс и базу правил в одном файле.
